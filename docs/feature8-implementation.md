The actual Thulasi-owned writer paths are therefore unavailable here to verify; this blocks enabling the dependent mutation.
- Existing request cancellation locks and revalidates the actor/session, then Hospital and HospitalRequest, and counts active/issued Allocation rows while the request lock is held. Any allocator must lock the same request before unit/allocation rows. This known path alone cannot establish compatibility with the absent issue, discard, expiry or deallocation writers.
- The approved domain rules do validate the lifecycle vocabulary: BloodUnit supports `AVAILABLE`, `ALLOCATED`, `ISSUED`, `EXPIRED`, `DISCARDED`; Allocation supports `ALLOCATED`, `ISSUED`, `CANCELLED`; active Allocation uniqueness is enforced by the generated active-unit key. Reservation is `ALLOCATED`, request `PARTIALLY_FULFILLED` includes reserved units and uses `ALLOCATION_UPDATED`, and `FULFILLED` requires all requested units to be `ISSUED`. Cancelling an unissued allocation must retain the Allocation row and return the unit to `AVAILABLE` if usable/unexpired or `EXPIRED` otherwise. These are documented rules, but the writer operations implementing them are absent.
- Read-only `information_schema` inspection of the actual MySQL 9.1 schema confirmed the AuditEvent column widths/nullability, the Allocation subject whitelist, and that no index exists on `operation_id`. The proposed payload is schema/writer-compatible: `ALLOCATION_CREATED` is 18 printable ASCII characters within `action_code VARCHAR(48)`; `Allocation` is an allowed `subject_type`; the actor Account ID is a positive BIGINT foreign key and the Allocation subject ID is a positive BIGINT scalar (AuditEvent intentionally has no subject FK); the fixed summary fits `change_summary VARCHAR(1000)`; NULL `reasonCode` is accepted; and a server UUID fits the writer's `operationId` validation/`CHAR(36)`. The action is **not** present in a production writer registry and has not been activated. `AuditEvent.operation_id` is not unique or indexed, and the read API does not expose it as a reconciliation filter.

The schema has no allocation idempotency key/table. A safe no-migration request protocol would need to bind confirmation to the exact FEFO unit IDs the Admin reviewed, revalidate that exact set under locks, and return a conflict if the same units are no longer available (never select replacement units on a repeated POST). An uncertain commit must return an outcome-unknown response, require a fresh request-detail/preview reconciliation, and never auto-retry. This is not implemented or concurrency verified.

## Transaction and audit handoff

The storage and read-only selector do not yet implement a production allocation transaction. Proposed common order for allocation, issue, cancellation, discard and expiry writers:

1. Lock the acting ACTIVE Admin Account row, then validate the authoritative stored SID on the same connection. For trusted expiry work, use the separately reviewed system actor/context.
2. Lock the HospitalRequest row.
3. Lock all candidate BloodUnit rows in ascending `blood_unit_id` order.
4. Lock relevant existing Allocation rows in ascending `allocation_id` order (including active allocations for the candidates).
5. Recheck request state/capacity, compatibility, donation approval, unit status, intended issue date and allocation uniqueness under these locks.
6. Set the verified RequestStatusHistory actor/reason connection context, update unit/allocation rows, then update HospitalRequest. The existing trigger writes history exactly once and checks the active actor/reason. Clear context before releasing the connection.
7. Insert audit rows on the same transaction connection, then commit. Any error rolls back all writes; failed rollback or uncertain commit destroys the connection and is never blindly retried.

This is a proposal for review with Thulasi and all future inventory writers; it is not concurrency verified. RequestStatusHistory already accepts `ALLOCATION_UPDATED` when moving to `PARTIALLY_FULFILLED`; `FULFILLED` is reserved for issued units. The AuditEvent writer has no allocation action in its approved registry. Proposed action for review: `ALLOCATION_CREATED`, subject `Allocation`, one event per unit with a shared server-generated operation ID and fixed summary. Do not add it to a production registry until reviewed. The existing `HOSPITAL_REQUEST_STATUS_CHANGED` action covers request status changes only and should not stand in for allocation traceability.
