# Preliminary API Design

This document is the API contract baseline. The bounded authentication/Donor work, Admin Donor Management, Hospital Registration/Profile, and Admin Hospital reads implement routes marked **Implemented subset** or **Implemented bounded subset**; all other listed endpoints remain planned, not implemented. Endpoints use JSON over HTTP. Request/response property names are camelCase; database column names remain snake_case. State, outcome, role, and priority codes use the exact uppercase values defined in `domain-rules.md` and `database-design.md`; screens may display title-case labels. Protected routes use the server-side authenticated principal; clients must not select their role or override ownership by submitting actor/hospital/donor identifiers. Every protected request checks current account status, role, and resource ownership. Routes marked **Approved addition** remain approved contracts for later work. Unless an operation is expressly allowed to PENDING accounts below, operational endpoints require an ACTIVE account; Admin operations require an ACTIVE Admin.

## Authentication and accounts

The [manual first-Admin CLI](first-admin-bootstrap.md) is an out-of-band local utility, not an API endpoint or public registration path. It creates one new ADMIN/ACTIVE Account only when no Admin exists; it neither changes an existing Account nor implements the shared approval/status routes below. USER-RUN evidence with browser confirmation reported 2026-10-26 records successful first-Admin creation and the basic authenticated Admin Hospital read flow; the guide separates this evidence from the earlier automated tests and lists the remaining live boundaries.

For the implemented Donor self-profile PATCH, text maxima count Unicode code points after trimming. A selected `reportedBloodGroupId` must exist in BloodGroup within the update transaction; a malformed/missing ID or applicable FK race produces a safe field validation error (422) without partial changes. This is a self-report, not operational group confirmation; no inactive-group eligibility/allocation policy is defined here. `email`, `dateOfBirth`, `confirmedBloodGroupId`, identifiers, role, account status, passwords/hashes, and timestamps are not accepted in the payload. The server also returns authentication/state errors (401), wrong-role errors (403), and missing-profile/storage failures (503) without exposing SQL or credentials. The update reads the saved profile on the transaction connection and responds only after commit; a zero affected-row count for identical values is not treated as missing.

The Admin Donor contract is specified in [Admin Donor Management](admin-donor-management.md). Its PATCH never accepts `reportedBloodGroupId`; confirmed-group selection is a separate staff-only action. Existing BloodUnit history is preserved, and incompatible history returns a conflict. It does not introduce an inactive BloodGroup policy or a confirmed-group clearing operation.

The bounded Donation POST accepts a plain object and a canonical unsigned BIGINT string `bookingId`. `COLLECTED` requires an explicit valid `+05:30` timestamp (seconds preserved) on the current appointment date, no later than server time and no earlier than slot start, check-in, or the applicable ACCEPTED decision. A collection can occur after the scheduled slot end on the same date. Its trimmed nonblank collection reference is at most 80 Unicode code points without controls and is unique. `INCOMPLETE` and `DEFERRED` reject both collection fields even when supplied as `null`. The server sets `PENDING` release for collected and `NOT_REQUIRED` for other outcomes. A current ACTIVE Donor and same-owner checked-in, non-cancelled-slot booking without a Donation and a same-day final decision are required. `COLLECTED`/`INCOMPLETE` require latest same-visit `ACCEPTED`, current donor-wide eligibility, and the 56-calendar-day interval since the latest COLLECTED outcome regardless of release; `DEFERRED` requires latest same-visit `TEMPORARILY_DEFERRED`. `REVIEW_REQUIRED` does not finalize a visit. The actor's stored SID is revalidated after domain waits. A successful transaction inserts exactly one Donation, changes exactly one Booking to `COMPLETED`, and writes `DONATION_RECORDED` plus `BOOKING_COMPLETED`; duplicate/stale requests return a safe conflict. Recording creates no BloodUnit. The two GET operations interpret `from`/`to` as inclusive IST **recording** dates based on `Donation.created_at`, sorted `created_at DESC, donation_id DESC`; donor ownership is session-derived. Testing approval, corrections, historical backfill, and unit creation remain separate work. See [the bounded milestone guide](donation-processing.md).

The two implemented Hospital Profile routes use shared session/current-account/HOSPITAL guards and return HTTP 200 with `Cache-Control: no-store`. ## Session behavior

Use server-side sessions with the custom MySQL-backed `app_session` store in `database/infrastructure/auth_sessions.sql`; runtime table creation is disabled and the store is not a domain entity or sample-data table. The implemented cookie is named `bdcs.sid`, `HttpOnly`, `SameSite=Lax`, path `/`, finite (default 120-minute) expiry, and `Secure` in production. Login rotates the session identifier; logout clears the cookie and tombstones the old session ID (`revoked_at` set, payload cleared). Saves and touches cannot restore revoked or expired rows. The store supports transaction-scoped account-wide tombstone revocation for approval, suspension and reactivation through an explicitly supplied connection. Password change remains unimplemented. Tombstones are retained because removing one while an old request is in flight could permit a stale insert; safe cleanup remains a later deployment decision. Every protected guard locks Account then the authoritative SID and checks current role/status, stored matching principal, payload, tombstone and expiry with fresh post-row-lock time. Missing/revoked/expired/mismatched SIDs fail even after a complete ACTIVE -> SUSPENDED -> ACTIVE cycle. Donor/Hospital profile writes repeat that check on their transaction connection before domain writes. The [status protocol](account-status-backend.md#authoritative-session-authorization-and-in-flight-requests) defines the authorization point: an already authorized read may finish; a profile write that wins the locks may commit before waiting suspension, and committed work is not undone. Legacy authenticated sessions without the state snapshot must sign in again. PENDING Donor/Hospital accounts may authenticate only to inspect approval status, read/update permitted own-profile fields, change password, and log out; all operational actions require ACTIVE status. The bounded Donor integration permits PENDING/ACTIVE Donors to update full name, phone, address, area, and reported blood group; confirmed group stays protected. The bounded Hospital integration permits PENDING/ACTIVE Hospitals to update only contact name, phone, and address. SUSPENDED accounts cannot establish sessions; suspension revokes existing sessions. Reactivation is an audited staff action and requires fresh login; previously revoked sessions remain invalid.

Password change at `POST /api/auth/password` remains unimplemented. When authorized, it must require the current password and validate `newPassword` server-side using the registration policy below, store only a bcrypt hash, audit without password values/hashes, and revoke every account session including the current one. Public password recovery is out of scope.

### Implemented authentication security details

- One shared password policy is used for Donor/Hospital registration and reserved for future password changes: at least 8 Unicode code points; at most 72 UTF-8 bytes; at least one Unicode number and one punctuation/symbol; spaces are allowed but do not count as symbols; no uppercase/lowercase combination is required; reject Unicode control characters. Never trim, normalize, truncate, log, or echo password values. bcrypt work factor is 12.
- Login rejects passwords over 72 UTF-8 bytes before bcrypt comparison and preserves accepted input exactly. It does not apply registration composition rules to existing credentials; invalid login responses remain generic.
- Cookie-authenticated unsafe requests (Donor/Hospital registration, login, logout, and Donor/Hospital self-profile PATCH) require a session-bound 256-bit random CSRF token in `X-CSRF-Token`. Obtain it from `GET /api/auth/csrf`; the frontend requests it before profile saves and keeps it in memory. Requests from a supplied Origin must match the configured frontend origin. Credentialed CORS permits only that exact origin, including PATCH preflight.
- Donor registration, Hospital registration, and login each have independent five-attempt per-client-IP fixed 15-minute limits. The bounded in-process limiter is per Node process; it is not shared across multiple workers/instances. Behind a reverse proxy, `req.ip` reflects the direct connection unless a narrowly trusted proxy is configured; do not trust arbitrary forwarded headers.
- Database errors map to safe codes/messages. API responses never contain password hashes, submitted passwords, session IDs, or raw driver details. Registration returns a pending account identity but does not authenticate it.
- `GET /api/auth/me` returns only Account identity/role/status and does not query the Hospital table. `GET/PATCH /api/donors/me` require the Donor profile schema; missing database/profile dependencies fail closed with a safe service error. PATCH uses a fixed SQL column allowlist, updates `Donor.updated_at` explicitly, and treats identical submitted values as success; validation, missing profile, authorization, and database failures use safe errors. Both profile responses are `no-store`.
- The client clears cached identity and Donor profile state and returns protected views to sign-in on a `401` with `AUTHENTICATION_REQUIRED` or `ACCOUNT_UNAVAILABLE`. Invalid-login `401` (`INVALID_CREDENTIALS`) and transient `503` responses do not revoke cached identity. Response handling does not retry protected requests automatically.

### Validation and error expectations for approved additions

- All path identifiers must parse as valid existing identifiers. Return the safe `not found` error for missing or out-of-scope records; do not reveal a Hospital's records to another Hospital.
- Admin donor, Hospital, unit, and request reads require an ACTIVE Admin. Return only the response fields listed in their route rows. Hospital-facing request list/detail responses must not include donor identity, unit-level donor provenance, or staff-only notes.
- The implemented `GET /api/admin/hospitals` validates/normalizes search, account-status filter, and pagination; it returns only management fields, not credentials or hashes. `GET /api/admin/hospitals/{hospitalId}` currently returns the identified Hospital profile only; the approved operational request summary remains deferred rather than fabricated.
- `GET /api/admin/requests/{requestId}` includes allocation history belonging only to that request, with unit ID/group/expiry and allocation status/timestamps. The detail read is Admin-only and does not expose donor identity or staff-only notes.
- Request review, allocation, cancellation, discard, issue, and expiry operations must validate the canonical transition and current allocation-derived quantities under the shared concurrency strategy; terminal request states are not reopened.
- `POST /api/auth/password` requires an authenticated non-suspended session and a valid CSRF token, a non-empty current password that verifies against the stored bcrypt hash, and a server-valid new password under the shared registration policy above. Expected safe errors include unauthenticated, forbidden/suspended, invalid current password, password validation failure, CSRF failure, and rate-limit response. Do not echo submitted passwords or return hashes.
- Common safe errors include validation failure, unauthenticated, forbidden, not found, invalid transition, conflict, and rate limited. Responses must not expose SQL, stack traces, credentials, hashes, donor identity to Hospitals, or staff-only notes.

`SESSION_SECRET` must be privately configured with at least 32 random UTF-8 bytes; `SESSION_TTL_MINUTES` is optional and defaults to 120 (allowed range 5–1440). Authentication fails closed if session configuration, database connection, or manually created session table is unavailable. The in-process limiter is suitable only for single-process development; shared rate-limit storage is a later deployment decision.

The bounded release contract is described in [release and inventory guide](release-inventory.md). The server sets `release_decided_at` from fresh IST time, never accepts the older planned client `decidedAt`, and stores `STAFF_RELEASE_APPROVED` for approval or the selected rejection code. The selected active BloodGroup is staff-confirmed for this unit only; this operation does not update `Donor.confirmed_blood_group_id`. An existing, different confirmed Donor group causes 409 instead of silent overwrite. A replay of the identical approval or rejection returns the prior decision without an extra unit or audit event. Response fields are limited to safe identifiers, group code, dates, statuses and replay flag. No detailed lab result is stored.
