# Eligibility and Slot Booking Milestone

This bounded application milestone uses the existing `DonationSlot`, `Booking`, `EligibilityDecision`, `Donation`, `Account`, `Donor`, and `AuditEvent` schema. It adds no migration or seed. Thulasi owns this domain's API and UI work; Lathikaa retains AuditEvent ownership. The audit writer is called on the same transaction connection as each successful mutation.

## Implemented boundary

ACTIVE Donors can read an advisory eligibility preview, browse future OPEN slots with appointment-date eligibility, list their own bookings, book a slot, and cancel their own `BOOKED` reservation before the slot starts. ACTIVE Admins can list slots and bookings, create future slots, edit capacity or an unbooked future schedule, close a future slot, cancel a future slot after checking that no booking is `CHECKED_IN`, check in an eligible current appointment, and record a bounded day-of decision for that checked-in visit. Slot cancellation changes still-`BOOKED` rows to `CANCELLED_BY_STAFF`; history remains. PENDING and SUSPENDED accounts cannot perform these operational actions. All mutations use the existing session, current Account/status checks, CSRF/origin protection, parameterized SQL, no-store responses, and safe error codes.

The implemented routes include `GET /api/donors/me/eligibility`, `GET /api/donation-slots`, `POST /api/admin/donation-slots`, `PATCH /api/admin/donation-slots/:slotId`, `GET /api/donors/me/bookings`, `POST /api/donors/me/bookings`, `POST /api/donors/me/bookings/:bookingId/cancellation`, `GET /api/admin/bookings`, `PATCH /api/admin/bookings/:bookingId/status`, and `POST /api/admin/donors/:donorId/eligibility-decisions`. Screen 6 supports advisory status plus the latest saved decision; Screen 7 and 8 support donor slot/booking work; Screen 18 supports slot management; Screen 19 now supports check-in and day-of decision actions for eligible rows. Donor pages use Rose Quartz Focus and Admin pages use Mint Gauge. The 30-screen baseline does not change.

### Check-in and day-of decision subset

- `PATCH /api/admin/bookings/:bookingId/status` accepts exactly `{ bookingStatus: "CHECKED_IN", reason: "STAFF_CHECKED_IN" }`. Only `BOOKED -> CHECKED_IN` is allowed, for an ACTIVE Donor with an existing Donor profile and a non-cancelled slot, when server time is `starts_at <= now < ends_at`. A `CLOSED` slot retains its appointments and permits check-in. Repeated/stale transitions conflict. Check-in preserves occupied capacity and creates no Donation.
- Authentication failures for the acting Admin remain `401 ACCOUNT_UNAVAILABLE`. A missing/wrong-role target Donor is reported as not found, and an inactive target Donor is a target-state conflict; neither target response invalidates the authenticated Admin session. The frontend validates the complete response against the captured booking, Donor, decision, fixed reason, exact deferred date (including null for other decisions), and a valid returned decision ID. An incomplete/mismatched success response is treated as uncertain and recovered with a read.
- `POST /api/admin/donors/:donorId/eligibility-decisions` in this bounded subset requires `{ bookingId, decision }`, plus `deferredUntil` only for `TEMPORARILY_DEFERRED`. The booking must belong to the path Donor, remain `CHECKED_IN`, have no Donation, and have an appointment on the current Asia/Kolkata date. Its Donor Account must remain ACTIVE. No `reasonCode`, `safeNote`, free-text medical answer, actor or timestamp is accepted.
- Supported decisions map to fixed audit reasons: `ACCEPTED` / `STAFF_ACCEPTED`, `TEMPORARILY_DEFERRED` / `STAFF_TEMPORARY_DEFERRAL`, and `REVIEW_REQUIRED` / `STAFF_REVIEW_REQUIRED`. A temporary date must be a valid calendar date on or after today's IST date, is shown in the confirmation as inclusive in IST, and other decisions reject a deferred date. ACCEPTED independently enforces the 56-calendar-day interval. It can supersede an earlier review/deferral but never waives that interval. A duplicate of the latest same-visit decision and deferral date conflicts; new decisions append to history. Latest ordering remains `decided_at DESC, eligibility_decision_id DESC`.
- Both actions lock actor and target Accounts in numeric order, then the actor's authoritative session SID, then domain rows following the existing booking-writer order. Preliminary booking identity reads are hints only and are revalidated under locks. The SID is revalidated after domain lock waits immediately before mutation; time-sensitive rules use fresh server time. Domain and audit writes share one transaction. Rollback/disposal and uncertain commit behavior use the existing transaction helpers. Mutations are never retried automatically.
- The existing booking response exposes only the minimum decision context needed by these screens (target Account active status for Admin rows, whether a Donation exists, and latest decision/date). Donors see only their own latest decision summary. No medical answers, private notes or other Donor data are added.
- This subset does not implement NO_SHOW, individual staff cancellation, COMPLETED, Donation creation, confirmed blood-group updates, or BloodUnit creation. A checked-in visit that is not accepted remains `CHECKED_IN` here; its later resolution is an OPEN question assigned to the separately documented Donation workflow.

## Eligibility and booking decisions

- The 56-day calendar interval is checked against the selected appointment's Asia/Kolkata date. The standalone preview uses the server's current Asia/Kolkata date. The latest `COLLECTED` Donation, regardless of release status, sets the interval date. With no collected donation, the interval does not block booking.
- The latest staff decision is ordered by `decided_at DESC, eligibility_decision_id DESC`. `REVIEW_REQUIRED` blocks booking until a later decision supersedes it. `TEMPORARILY_DEFERRED` blocks through `deferred_until` inclusive. A later `ACCEPTED` clears that review or deferral, but does not waive the independent collection interval. This preview is advisory; staff day-of acceptance is a later workflow.
- Only `BOOKED` and `CHECKED_IN` occupy slot capacity and count as active overlapping bookings. `CANCELLED_BY_DONOR`, `CANCELLED_BY_STAFF`, `NO_SHOW`, and `COMPLETED` remain history without occupying capacity. A donor cannot have overlapping active appointment windows. The schema's unique donor/slot key prohibits rebooking the same slot even after cancellation.
- Reducing capacity below occupancy is refused. Once any booking exists, schedule edits are refused. A cancelled slot cannot reopen. Closing a slot prevents new bookings without cancelling existing bookings. Donor cancellation uses the fixed `DONOR_REQUESTED` reason; slot cancellation uses fixed staff reason codes and audits each affected booking and the slot.

Slot create/update accepts a local timestamp in `YYYY-MM-DDTHH:mm+05:30` or `YYYY-MM-DDTHH:mm:ss+05:30` form. The server rejects impossible calendar dates, a missing/different offset, start/end inversion, nonfuture starts, and capacities outside integer 1–65535. Browser date-time inputs are converted explicitly to `+05:30`; display formatting specifies `Asia/Kolkata` and does not depend on the browser's local zone.

Transactional writes lock the actor Account and authoritative stored session before slot and booking rows. The already-locked SID is revalidated after domain waits immediately before the first mutation, sampling fresh expiry time; time spent waiting cannot authorize an expired session. Re-reading the held SID does not change lock ordering. Slot capacity is checked after locking the slot, and donor booking conflicts are serialized by the donor Account lock. Audit failure aborts the associated mutation. Existing transaction cleanup handles rollback, uncertain commit, and connection disposal. The frontend obtains fresh same-session CSRF before each mutation, freezes confirmation identity/action, prevents duplicate dispatch, and resolves uncertain outcomes with reads rather than automatic retries. The read-only list is not a capacity reservation; every mutation rechecks state.

Both fulfilled and rejected mutation results are ignored when their selection, query scope, or auth lifecycle is obsolete. The dispatch guard remains held until the request settles, including after filter or draft changes. Editing/discarding an Admin draft invalidates its pending confirmation and CSRF preflight. Capacity-only edits retain existing timestamp seconds and send only capacity. Known validation/access rejection responses remain definite rejections; transport failures, malformed success and explicit transaction uncertainty require read-only recovery.

The fixed AuditEvent action/reason pairs are `DONATION_SLOT_CREATED` / `SLOT_SCHEDULED`, `DONATION_SLOT_UPDATED` / `SLOT_DETAILS_UPDATED`, `DONATION_SLOT_CLOSED` / `STAFF_CLOSED`, `DONATION_SLOT_CANCELLED` / `STAFF_CANCELLED`, `BOOKING_CREATED` / `DONOR_RESERVED`, `BOOKING_CANCELLED_BY_DONOR` / `DONOR_REQUESTED`, `BOOKING_CANCELLED_BY_STAFF` / `SLOT_CANCELLED_BY_STAFF`, `BOOKING_CHECKED_IN` / `STAFF_CHECKED_IN`, and `ELIGIBILITY_DECISION_RECORDED` / the decision's fixed reason above. One slot cancellation can write its slot event plus one event per still-BOOKED row. The actor and operation ID are server derived; summaries are fixed, and refused attempts write no success event. This mapping is local to the bounded operation, using Lathikaa's unchanged audit writer.
