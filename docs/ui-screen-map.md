The map follows the approved scope, architecture, API design, and existing database entities. API operations are planned contracts, not implemented endpoints. Screen ownership follows complete feature ownership in `team-workflow.md`. Theme assignments remain OPEN for all screens.

## Shared UI requirements

- Provide role-specific navigation for Donor, Hospital, and Admin / Blood Bank Staff users.
- Provide loading, empty, success, and error states on applicable screens.
- Show clear validation messages near the relevant inputs and provide an understandable summary when needed.
- Use responsive layouts, accessible labels, and keyboard-accessible navigation.
- Hiding a link or action in the UI does not grant access control: backend authorization is required for every protected operation and resource.
- PENDING Donor/Hospital users may use the existing account/profile surfaces to view approval status, read/update permitted own-profile fields, change their password, and log out; operational actions require ACTIVE. SUSPENDED users cannot establish a session. These account states do not add screens to the baseline.
- Keep donation processing, testing/release approval, inventory availability, and request allocation distinct. A donation outcome is recorded during processing; a collected donation requires an approved release decision before its blood unit can become allocatable; inventory availability follows unit status and expiry rules; allocation applies compatibility and request rules transactionally. Allocation alone does not mean a unit has been issued or a request fulfilled.
- Show allocated/reserved quantity and issued quantity separately. `FULFILLED` requires exactly the requested quantity to be issued. Request workflow/status tracks must reflect the documented branches and cancellations rather than imply one linear path.
- All screens in this document remain planned until implemented and verified.

## Visual design status

Theme options are documented in `ui-design.md`; the user will choose an assignment for each screen later. All theme-assignment cells above remain OPEN.

Use consistent shared navigation across screens regardless of theme. Use reusable semantic tokens and components. Layouts must be responsive, keyboard navigable with visible focus, and use accessible labels/navigation. Check text and UI contrast. Provide loading, empty, success, and error states and support reduced motion. Status and emergency meaning must never rely on color alone. Dashboard metrics and inventory thresholds are not finalized here; do not invent them.
