# UI Screen Map

This is the 30-screen baseline. Routes marked proposed remain planned; the bounded authentication/Donor, Hospital, Admin Account, eligibility/booking, and Donation Processing surfaces listed below are implemented to their stated limits. Donor Profile supports own contact and reported-group editing while confirmed group and account details remain protected. The map follows the approved scope, architecture, API design, and existing database entities. API operations marked implemented are delivered runtime contracts; other operations remain planned. Screen ownership follows complete feature ownership in `team-workflow.md`. Rose Quartz Focus is selected for Donor eligibility/booking and Donation History; Mint Gauge is selected for Admin slot/booking and Donation Processing pages. Other unimplemented screen assignments remain OPEN.

## Shared UI requirements

- Provide role-specific navigation for Donor, Hospital, and Admin / Blood Bank Staff users.
- Provide loading, empty, success, and error states on applicable screens.
- Show clear validation messages near the relevant inputs and provide an understandable summary when needed.
- Use responsive layouts, accessible labels, and keyboard-accessible navigation.
- Hiding a link or action in the UI does not grant access control: backend authorization is required for every protected operation and resource.
- PENDING Donor/Hospital users may use the existing account/profile surfaces to view approval status, read/update permitted own-profile fields, change their password, and log out; operational actions require ACTIVE. SUSPENDED users cannot establish a session. These account states do not add screens to the baseline.
- Keep donation processing, testing/release approval, inventory availability, and request allocation distinct. A donation outcome is recorded during processing; a collected donation requires an approved release decision before its blood unit can become allocatable; inventory availability follows unit status and expiry rules; allocation applies compatibility and request rules transactionally. Allocation alone does not mean a unit has been issued or a request fulfilled.
- Show allocated/reserved quantity and issued quantity separately. `FULFILLED` requires exactly the requested quantity to be issued. Request workflow/status tracks must reflect the documented branches and cancellations rather than imply one linear path.
- Screens without implemented routes remain planned. The surfaces marked implemented above are delivered only within their stated scope; Donor Profile and Account / Password Settings remain partial.

## Visual design status

Theme options are documented in `ui-design.md`. Rose Quartz Focus is selected for the implemented shared Login/Donor registration, access/error, bounded Donor Profile read/edit, Donor Dashboard, account status, password settings, and Screens 6–9. Hospital Registration, Hospital Profile, and Screen 24 Admin Hospital Management use scoped Mint Gauge colors, Sora headings, and Nunito Sans body/UI. Screens 18–20 use Mint Gauge for their implemented slot, booking, and Donation Processing subsets. Screen 24 uses rounded white cards, mint borders, a responsive table, explicit status text, and deep teal actions; it has no decorative gauges or fabricated statistics. Shared navigation placement is retained. All other unimplemented screen assignments remain OPEN. See [Hospital frontend verification](hospital-frontend.md), [Admin Hospital Management](admin-hospital-management.md), [eligibility/booking scope](eligibility-booking.md), and [Donor Dashboard and Password Settings](donor-dashboard-password-settings.md).

Use consistent shared navigation across screens regardless of theme. Use reusable semantic tokens and components. Layouts must be responsive, keyboard navigable with visible focus, and use accessible labels/navigation. Check text and UI contrast. Provide loading, empty, success, and error states and support reduced motion. Status and emergency meaning must never rely on color alone. Dashboard metrics and inventory thresholds are not finalized here; do not invent them.
