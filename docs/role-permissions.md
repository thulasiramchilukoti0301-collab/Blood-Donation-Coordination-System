The bounded authentication work implements public Donor/Hospital registration, login/logout, current-account status, Donor self-profile read/edit, and Hospital self-profile read/contact edit. Donor self-edits are limited to full name, phone, address, area, and optional self-reported blood group; confirmed group remains staff-controlled. The current bounded [Admin Donor Management feature](admin-donor-management.md) implements ACTIVE ADMIN list/detail reads and audited correction of the approved Donor fields or separate confirmed-group selection on Screens 16–17; Account status actions remain on the shared Account management page. Hospital registration atomically creates HOSPITAL/PENDING Account and Hospital rows without automatic login; see [its exact contract](hospital-registration-api.md). The Hospital Profile integration mounts own-profile GET and contact-only PATCH for PENDING/ACTIVE Hospitals with shared session/current-account/HOSPITAL guards and PATCH CSRF. Admin Hospital Management adds ACTIVE ADMIN-only list/detail reads and Screen 24, including read-only display of each Hospital's current Account status. The remaining permission matrix describes the approved broader application; only implemented routes listed in `api-design.md` are available. The shared Account queue and audited PENDING-to-ACTIVE approval backend are implemented for ACTIVE ADMIN only; basic USER-RUN Console approval/audit/fresh-login evidence dated 2026-10-26 is recorded in the Account approval guide; further live concurrency/failure/security and multi-device checks remain pending. The [Mint Account approval supporting flow](account-approval-frontend.md) now guards `/admin/accounts` for restored ACTIVE ADMIN sessions, with separate [USER-RUN Donor UI evidence](account-approval-frontend.md#user-run-frontend-evidence-2026-10-26); live Hospital approval, multi-page/mobile/tablet and edge-case UI checks remain pending. Audited DONOR/HOSPITAL suspension/reactivation are now [bounded backend operations](account-status-backend.md) for current ACTIVE ADMIN sessions, with exact controlled reasons and authoritative Account/SID checks. Separate [USER-RUN evidence reported 2026-10-27](account-status-backend.md#user-run-donor-status-cycle-evidence-reported-2026-10-27) records one Donor cycle through the Console and its observed sign-in/audit outcomes. ## Permission principles

- Default deny: each endpoint requires authentication and an explicit role/ownership check.
- A Hospital can see only its own profile and requests. A Donor can see only their own profile, bookings, and donation history. Admin / Blood Bank Staff can access operational records needed to run the bank.
- Public registration never creates an Admin account. The bounded [first-Admin CLI](first-admin-bootstrap.md) implements manual/out-of-band creation of one new ACTIVE Admin on an explicitly selected loopback development database; successful first-Admin creation and the basic Admin Hospital read/session flow have separate USER-RUN evidence with browser confirmation reported 2026-10-26. It refuses any existing Admin regardless of status, never promotes or resets an Account, and does not implement applicant approval.
- Every protected request checks the current account status, role, and resource ownership; a session cookie alone does not preserve access after status changes.
- PENDING Donor/Hospital accounts may authenticate only to view approval status, read/update permitted fields on their own profile, change their password, and log out. They cannot book, request blood, or perform other operational actions.
- SUSPENDED accounts cannot establish a session. Suspension revokes existing sessions. Reactivation requires an audited staff action and a fresh login; a revoked session is never restored.
- The implemented password change is authenticated, verifies the current password, validates the new password server-side using the registration policy, stores only a bcrypt hash, audits without password material, and revokes all account sessions including the current one. CSRF protection applies; successful change requires a fresh login. Public password recovery is out of scope. The owner-scoped Donor activity endpoint and Screen 4 require an ACTIVE Donor; PENDING Donors can still use password settings.
- Delete means logical cancellation/deactivation where history matters. Completed donations, allocations, issued units, audit events, and requests are retained; no user can hard-delete traceable history through the application.

## Permission matrix

Staff-created non-admin accounts and corrections to completed Donation records still lack API contracts. They remain policy/contract decisions to resolve as listed in `implementation-readiness.md`; this matrix does not authorize an undocumented endpoint or implementation. The broad Admin request-status permission does not resolve whether staff may cancel a request after partial issue. That permission and its operation contract remain OPEN; Hospital cancellation remains limited to before any unit is issued.

## Admin-only operations

The implemented Hospital management reads (`GET /api/admin/hospitals` and `GET /api/admin/hospitals/{hospitalId}`) require an authenticated current ACTIVE ADMIN. A PENDING or SUSPENDED target Hospital may be listed/viewed by that Admin; its state does not grant the target Hospital Admin permissions. The bounded Donor directory/detail routes likewise require an ACTIVE Admin; PENDING and ACTIVE Donors may be edited, while a SUSPENDED target returns a safe conflict. DONOR/HOSPITAL sessions cannot use these reads. PENDING/SUSPENDED ADMIN accounts cannot establish or retain a permitted protected session. Client-supplied actor IDs, roles or status never replace the verified server Account. Screen 24 has no status controls. Thulasi's shared `GET /api/admin/accounts` and `PATCH /api/admin/accounts/{accountId}` implement queue/bounded approval, suspension and reactivation with transactional audit/revocation; [exact subset and live limits](account-approval-backend.md) are documented. Basic Console approval observations are recorded separately in that guide. The shared `/admin/accounts` frontend implements the bounded account status controls. No Hospital-only Account update endpoint is authorized by the Hospital read integration.

Only an ACTIVE Admin / Blood Bank Staff account may: approve/suspend/reactivate accounts; correct approved Donor profile fields or explicitly select the confirmed blood group under the bounded Screen 17 contract; make final day-of donor acceptance/deferral; record bounded Donation outcomes; correct completed donations only after the OPEN correction contract is decided; approve/reject testing; create, discard, expire, allocate, deallocate, or issue blood units; review/reject hospital requests; change request priority/status on behalf of workflow; edit blood-group/compatibility reference data; access audit logs and system-wide reports. Any correction, override, account-state change, or reactivation requires reason and audit event. Reactivation invalidates old sessions; the account must log in again.

Hospital and Donor operational permissions in the matrix require `ACTIVE` account status. Pending users are limited to approval/status view, permitted own-profile read/update, password change, and logout. Suspended users cannot log in and have no valid protected requests; middleware/service logic checks current status on every request.

Hospitals cannot allocate units, view unit-level donor provenance, change staff decisions, or see other hospitals' requests. Donors cannot self-approve, record donations, alter eligibility outcome, or see other donors. User-supplied identifiers are never trusted in place of authenticated ownership.

## Search and filtering

### Admin / Blood Bank Staff

- Donors (implemented bounded Admin directory): full name, phone, area, decimal Donor ID, exact Account status, reported or confirmed blood group; 20-row pagination. Eligibility search and next-eligible-date filters remain planned.
- Bookings/donations: donor, slot/date range, booking/donation status, donation outcome/testing status.
- Inventory: blood group, exact unit ID, unit status, collection/expiry date range, available-only, expiry-soon.
- Hospitals (implemented reads): organization name, registration number, contact name or phone; exact Account-status filter (`PENDING`, `ACTIVE`, `SUSPENDED`); positive page number, fixed 20-row pages. No email, credentials, request summaries or arbitrary Account lookup is exposed.
- Hospital requests: hospital, request ID, status, priority, blood group, submitted/needed-by range, outstanding quantity.
- Audit: actor, entity type/id, action, date range.

### Hospital

- Own requests: request ID, blood group, status, priority, submitted/needed-by date range. Sort by newest, need-by date, or status. No inventory query by unit.

Feature 7's activated public Hospital list currently supports the documented structured filters with one stable newest-first order (`createdAt DESC, requestId DESC`), fixed 20-row pages, and no caller sort parameter. The broader selectable sorting above is future behavior, not an implemented option. ACTIVE Hospital/Admin accounts can use the request BloodGroup lookup; it returns active choices only, with no compatibility matrix. Existing requests remain readable after group deactivation.

### Donor

- Own bookings: status/date range.
- Own donation history: donation date range/status. Donor profile lookup is self-only; public directory/search of donors is not included.
