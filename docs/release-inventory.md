# Bounded Donation release and inventory visibility milestone

This extends the uncommitted [Donation Processing milestone](donation-processing.md) on `thulasiram`. It uses existing 003 Donor, 006 Donation, 007 BloodUnit, 010 AuditEvent, Account/session, Booking and BloodGroup structures. It adds no migration, seed, grant or dependency. Lathikaa retains Hospital request, Allocation and Audit feature ownership; the existing shared audit writer is reused. The [migration ledger](../database/migration-ledger.md) remains the source for separately attributed installation evidence. No MySQL connection or SQL application was performed in this implementation task.

## Exact release contract

`POST /api/admin/donations/{donationId}/testing-decision` is for an ACTIVE Admin with trusted Origin, fresh CSRF, current Account and authoritative stored SID. `donationId` and every group ID are canonical unsigned BIGINT strings. The body is a plain object with exactly one of:

- Approval: `{ "decision": "APPROVED", "confirmedBloodGroupId": "3" }`. The group must exist and be active. Staff select it explicitly; a Donor self-report never supplies it automatically. The operation records confirmation **for this unit only** and does not update `Donor.confirmed_blood_group_id`. If that profile field already holds a different group, the request conflicts and staff must reconcile it through a separately authorized workflow.
- Rejection: `{ "decision": "REJECTED", "reasonCode": "TESTING_NOT_APPROVED" }`. The required non-sensitive code is one of `TESTING_NOT_APPROVED`, `PROCESSING_ISSUE`, `OTHER_NON_SENSITIVE`. No detailed laboratory result, medical answer or free-text note is accepted.

Unknown fields, including the older planned client `decidedAt`, actor, unit/status/expiry, collection time, donor group and extra reason fields are rejected. Server time owns `release_decided_at`; approval stores `STAFF_RELEASE_APPROVED` and rejection stores the selected code in `release_reason_code`. Only a `COLLECTED` Donation with `PENDING` release and its completed, same-owner Booking can transition. `INCOMPLETE`/`DEFERRED` stay `NOT_REQUIRED`; a rejected Donation has no unit.

Success returns `success: true` and `release` with `donationId`, `decision`, `reasonCode`, server `releaseDecidedAt` in `+05:30`, `replayed`, and `unit` (null on rejection; on approval, unit ID, source Donation ID, group ID/code, expiry date and current status). Identical APPROVED replay with the same group or identical REJECTED replay with the same reason is read-only: it returns the prior decision and unit without another audit event. Changed decision/group/reason, a missing linked unit for a previously approved Donation, or another stale state returns safe 409 `RELEASE_CONFLICT`. A duplicate unit key is a final database backstop. No ambiguous POST is automatically retried.

## Transaction, expiry and audit

The writer locks actor and donor Accounts in numeric order, then the authoritative actor SID, followed by Donor, slot, Booking, Donation, BloodGroup (approval), and BloodUnit. This is the coordinated order for this bounded release operation; future Allocation/inventory writers must agree on a shared order before integration. A preliminary Donation/Booking owner lookup is a hint and every relation is rechecked under locks. The SID is revalidated after all domain waits, immediately before writing. Fresh server time is sampled then. The IST collection date plus 42 calendar days yields `expiry_date`; a new unit starts `AVAILABLE` only if today's IST date is strictly before expiry, otherwise `EXPIRED` with `expired_at` set. No status/expiry value comes from the client.

A conditional affected-row checked Donation release update, one BloodUnit insert for approval, and mandatory audit writes share one transaction connection. Approval writes `DONATION_RELEASE_DECIDED` on Donation with `STAFF_RELEASE_APPROVED`, and `BLOOD_UNIT_CREATED` on BloodUnit with `APPROVED_DONATION`; the two events share a server operation UUID. Rejection writes only `DONATION_RELEASE_DECIDED` with its selected reason. Summaries contain state or unit status only, never names, contact information, collection references, credentials, session data or medical answers. Failure rolls back; failed cleanup destroys the connection, and uncertain commit returns `TRANSACTION_OUTCOME_UNKNOWN` rather than saved success. These properties have injected/database-free checks, not live MySQL confirmation.

## Inventory reads and lifecycle controls

- `GET /api/inventory`: ACTIVE Admin only, 20 rows per page ordered by `expiry_date ASC, blood_unit_id ASC`. Validated optional `bloodGroupId`, `unitStatus`, `availableOnly=true|false`, `collectedFrom/To`, `expiresFrom/To`, and `page` filters. `availableOnly=true` requires persisted `AVAILABLE`, approved release and expiry strictly after today's IST date. The response distinguishes persisted `unitStatus` from `effectiveAvailability`; an AVAILABLE unit whose expiry date is due remains persisted AVAILABLE until reconciliation, but is not effectively available. `expiryDue` identifies that case. It returns safe unit/source summaries, total and pagination; `expirySoon` remains a planned filter.
- `GET /api/admin/inventory/{bloodUnitId}`: ACTIVE Admin only. Returns the unit's group, status, expiry, source Donation ID/outcome/release and collection/release dates. A deactivated historical BloodGroup remains readable. `allocations: null` means Allocation history is unavailable until Lathikaa's reviewed module is integrated. It contains no Donor identity, collection reference or staff note.

`POST /api/admin/inventory/expiry/run` is an explicit ACTIVE Admin operation with trusted Origin and fresh CSRF; its body is `{}`. The transaction locks Accounts in numeric order (the actor only here), then the authoritative Admin SID, then AVAILABLE/ALLOCATED BloodUnit rows in expiry/ID order. It rechecks the SID after domain locks, samples fresh IST date/time, and expires every due AVAILABLE row with `expired_at` plus one `BLOOD_UNIT_EXPIRED` event (`EXPIRY_RECONCILIATION`, `AVAILABLE -> EXPIRED`) per row. A repeat run is safe and returns zero additional expirations. If any due ALLOCATED row exists, it returns `ALLOCATION_COORDINATION_REQUIRED` and rolls back all work in that run; Allocation cancellation and request-state recomputation are not integrated. ISSUED, EXPIRED, and DISCARDED rows are never changed. No MySQL scheduler or scheduled job is implemented.

`POST /api/admin/inventory/{bloodUnitId}/discard` accepts exactly one bounded reason code: `DAMAGED`, `PACKAGING_COMPROMISED`, `TEMPERATURE_EXCURSION`, or `OTHER_NON_SENSITIVE`. Under Account -> authoritative SID -> BloodUnit lock order it rechecks the SID after the unit lock, samples fresh IST date/time, and permits only an unallocated, unexpired persisted AVAILABLE unit. Due units return `UNIT_EXPIRY_DUE`; ALLOCATED units return `ALLOCATION_COORDINATION_REQUIRED`; ISSUED/EXPIRED/DISCARDED return a safe status conflict. Success sets `DISCARDED`, `discarded_at` and `discard_reason_code`, and writes `BLOOD_UNIT_DISCARDED` with a state-only summary in the same transaction. It preserves the Donation, group, expiry and unit history. The DDL has no EXPIRED-only timestamp check; the service always sets `expired_at` when it transitions a due AVAILABLE row.

Mint Gauge Screen 21 (`/admin/donations/testing`) reviews PENDING COLLECTED Donations from the existing Admin history GET. Its frozen confirmation shows Donation/Booking, collection time, decision, group or rejection reason, and the unit consequence. Cancel sends no POST. Screens 22 (`/admin/inventory`) and 23 (`/admin/inventory/:bloodUnitId`) remain existing baseline entries; inventory search distinguishes effective availability and offers explicit expiry reconciliation and discard controls for eligible rows. Fresh CSRF, auth lifecycle/selection checks, duplicate guards, response validation, GET-only uncertainty recovery, focus/Escape and responsive layouts follow existing Admin patterns. A dispatched mutation is never automatically retried; uncertain outcomes trigger reads only. A confirmed save followed by failed list refresh is reported separately from an unconfirmed POST. Backend authorization remains authoritative.
