## Visit and authorization contract

- Only a verified ACTIVE Admin with an authoritative stored SID records an outcome. The target must remain an ACTIVE DONOR with a Donor profile, and the checked-in Booking must belong to that Donor, have a non-CANCELLED slot and have no Donation yet. Preliminary owner/slot lookup is a hint; the rows are checked again under locks.
- The slot appointment and latest same-visit decision must be on the current Asia/Kolkata calendar date. The decision must belong to that Booking and Donor. `REVIEW_REQUIRED` is unresolved and cannot finalize the visit; a later supported final decision is required. An old/ended slot or absence of collection never implies a DEFERRED outcome.
- `COLLECTED` and `INCOMPLETE` require latest same-visit `ACCEPTED`, current donor-wide decision/deferral eligibility, and the independent 56-calendar-day interval since the latest `COLLECTED` Donation regardless of later release status. A later donor-wide blocking decision from another visit blocks collection. `DEFERRED` requires latest same-visit `TEMPORARILY_DEFERRED` and does not require collection eligibility; outcome recording does not add or alter decision history.
- `COLLECTED` means successful collection; `INCOMPLETE` means an accepted attempt did not complete; `DEFERRED` means the visit ended without collection after staff temporary deferral. Every permitted outcome inserts one Donation and changes exactly one `CHECKED_IN` Booking to `COMPLETED` in the same transaction. `COMPLETED` means visit resolved, not necessarily collected. Cancelled and NO_SHOW bookings cannot create Donation rows.
- For `COLLECTED`, the request requires a strict explicit `+05:30` timestamp with calendar and seconds preserved. It must be today IST, no later than fresh server time, and no earlier than slot start, check-in or applicable acceptance decision. Same-day collection after the scheduled slot end is permitted. A trimmed, nonblank, unique collection reference has at most 80 Unicode code points and no control characters. `INCOMPLETE`/`DEFERRED` reject both collection properties even when sent as `null`, and store them as NULL. The server/database own recording/status/audit timestamps. Initial release is `PENDING` for `COLLECTED`, otherwise `NOT_REQUIRED`.
- Account locks are acquired in ascending numeric ID order, then the actor SID, followed by Donor/profile, slot, Booking, same-visit decision and donor history with locking/current reads. The SID is rechecked after domain waits and immediately before the first write. Fresh time is sampled then. Donation insert, one conditional Booking completion, and both audit writes share the caller's transaction connection. The audit writer does not begin or commit a separate transaction. Duplicate/stale outcomes are safe conflicts; failed work rolls back, and uncertain commit/cleanup is not reported as saved.

## Runtime API and screens

| Contract | Implemented subset |
|---|---|
| `POST /api/admin/donations` | ACTIVE Admin, same-session CSRF and trusted Origin. Exact plain JSON allowlist: `bookingId` (canonical positive unsigned BIGINT string), `outcome`, plus `collectedAt` and `collectionReference` for COLLECTED only. Returns a persisted safe Donation summary only after commit, including `COMPLETED` Booking status. No actor, group, release decision, medical answer or audit field is client-writable. |
| `GET /api/admin/donations` | ACTIVE Admin search by `donorAccountId`, `outcome`, `releaseStatus`, inclusive IST recording dates `from`/`to` and `page`. Twenty rows per page ordered by `Donation.created_at DESC, donation_id DESC`; minimal Donor name/ID, booking and outcome fields. |
| `GET /api/donors/me/donations` | ACTIVE Donor only; ownership derives from the current session. `from`/`to`/`page` have the same recording-date meaning and pagination. High-level outcomes, dates, release status, safe IDs and `nextEligibleDate` from the latest COLLECTED outcome are returned. Collection references, staff-private details and other Donors' records are excluded. |

Screen 20 at `/admin/donations/process` uses Mint Gauge. It selects an eligible checked-in visit from the existing Admin Booking response, shows identity/appointment/decision, captures only applicable fields, confirms the exact action and its Booking completion, and provides read-only Donation search. Screen 9 at `/donor/donations` uses Rose Quartz Focus and is read-only. Both are bounded surfaces within the existing 30-screen baseline. The UI states clearly that recording never creates an inventory unit; `COLLECTED` with `PENDING` release is not approved stock. Fresh CSRF, captured response validation, duplicate guards, auth/draft/query lifecycle checks and GET-only uncertainty recovery are used. The backend remains authoritative. At this earlier recording milestone, Screen 21 release approval and BloodUnit creation were planned; the later bounded implementation is in [release/inventory](release-inventory.md).

Audit writes use a local action allowlist: `DONATION_RECORDED` on Donation with `COLLECTION_RECORDED`, `INCOMPLETE_ATTEMPT_RECORDED` or `DEFERRED_VISIT_RECORDED`, followed by `BOOKING_COMPLETED` on Booking with `DONATION_OUTCOME_RECORDED` and fixed `CHECKED_IN -> COMPLETED` summary. Both use the verified Admin actor and the same operation UUID. Summaries contain no name, contact detail, collection reference, credential, session material or medical answer.
